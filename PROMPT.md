# Prompt: build "Dev break" (human-in-the-loop) from scratch

Give this whole file to a coding agent. It describes the complete app; build it, run it, and verify every feature.

---

Build **Dev break**, a Windows tray app that gives a developer a short brain break from working with AI: once an hour
it pops up a computer-science / architecture question generated by the `claude` CLI, lets them answer, scores the
answer, shows a model answer, and lets them discuss it with Claude in a side panel. The same window has a **learn
path**: a course per topic, written by Claude, from the theory to what every senior engineer should know, with real
examples; and a daily **TL;DR** per topic, written from the web, every item explained for the developer's own stack,
which they can save into their own Claude Code memory or skills. Discussions may look at the developer's machine,
read-only. It is
**gamified**: XP and ranks, a daily streak and goal, badges, and a stats screen; weak topics are asked more often.
The look is light and simple: a compact card, topic chips, three buttons, settings behind a gear.

## Tech

- C# WPF on .NET 10 (`net10.0-windows`), `UseWPF` + `UseWindowsForms` (WinForms only for the tray `NotifyIcon`).
  Nullable enabled, implicit usings off, `NoWarn WPF0001`. Assembly/namespace `DevBreak`.
- `App.xaml`: `ThemeMode="System"` (Fluent theme, follows light/dark), `ShutdownMode="OnExplicitShutdown"`.
  Use `AccentButtonStyle` for the main button.
- No NuGet packages. No database. Everything AI goes through the user's own logged-in `claude` CLI.
- `profile.txt`: `<None Update="profile.txt" CopyToOutputDirectory="PreserveNewest" ExcludeFromSingleFile="true" />`.
- Single-file publish: `dotnet publish -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -o publish`.
- `.gitignore`: `bin/ obj/ publish/ *.user .vs/ profile.txt .claude/ learn/ game.json topics.json`. MIT license.

## Calling Claude (`QuestionGenerator.RunClaudeAsync`)

Start `claude` as a child process with arguments (use `ArgumentList`):
`-p --tools "" --strict-mcp-config --setting-sources "" --no-session-persistence`
- Working directory: the temp folder. No window. Write the prompt to **stdin** as UTF-8 without BOM, then close stdin.
  Read stdout/stderr as UTF-8. Timeout 3 minutes. Non-zero exit → exception with stdout + stderr. On timeout kill the
  whole process tree. Start the process off the UI thread (`claude.exe` is large and takes ~0.5 s to start).
- Do NOT use `--bare` (it fails with "Not logged in").
- `RunClaudeAsync(prompt, web: true)` (only the TL;DR): the same with `--tools "WebSearch,WebFetch" --allowedTools
  "WebSearch,WebFetch"` instead of `--tools ""` (allowed up front, because `-p` cannot ask).
- Discussions use their own run, see **Discussions** below.

## Levels (by time of day)

`record Level(Name, Style, Topics)`; `Level.At(time)`: before 12:00 Heavy, 12:00-15:00 Medium, after 15:00 Light.
- **Heavy**: "an architecture / system-design decision with real trade-offs (2-4 options to choose between)".
  Topics: distributed systems, caching strategy, database design and scaling, consistency and transactions, messaging
  and event-driven design, API design, microservices vs monolith, security architecture, observability and reliability,
  cloud cost and scaling, data pipelines.
- **Medium**: "a focused technical question that needs some reasoning". Topics: algorithms and complexity, data
  structures, concurrency, SQL and indexes, JVM internals, networking and HTTP, operating systems, Spring and JPA,
  testing strategy, design patterns.
- **Light**: "a quick question answerable in under a minute (a short snippet, a definition, a "what does this print")".
  Topics: Java language trivia, git, HTTP status codes, Linux / shell commands, regex, JavaScript quirks, SQL
  basics, CS history, computer architecture basics, encoding and Unicode.

## Tabs (categories) - the user's own topics (`Topics.cs`)

`record Category(Name, Topics)`; `TopicsFor(level)` returns its own topics, or the level's topics when it has none.
`Category.All` = **Mix** (no topics; uses the level's list) followed by the user's chosen topics. Nothing is
hard-coded: the topics are saved as `[{"Name":..., "Topics":[...]}]` in `topics.json` next to the exe (git-ignored).
`Topics.IsSetUp` = that file exists. `Topics.Save(chosen)` writes it, keeps the existing `Category` instances for
unchanged topics (open tabs and queued questions stay attached) and raises `Topics.Changed`.

- **`SuggestAsync()`**: read the user's typed Claude Code prompts exactly as for "Knowledge" below
  (`Knowledge.RecentPrompts()`: last 7 days, newest 200). No prompts → return an empty list without calling Claude.
  Otherwise prompt: "Below are a developer's own recent prompts to an AI coding assistant and the names of the project
  folders they worked in. Suggest up to 10 topics this developer would gain from learning more about, based on the
  technologies and engineering problems they work with." + "Only general, public high-tech topics (software, data,
  cloud, AI, security, networks, hardware, engineering practice). Never anything personal or private: no health,
  family, money or personal life, nothing about the user's employer, company, customers, products or business, no
  people's names, no internal project names." + "Each topic is a short tab name (1-3 words, e.g. "PostgreSQL",
  "Kubernetes", "System design") with 4-8 sub-topics." Reply one per line: `<tab name> | <sub>; <sub>; <sub>`,
  followed by `PROJECT FOLDERS:` and `PROMPTS (newest first):`.
- **`ShapeAsync(wish)`**: what the user typed ("I want to learn business regulation on PII") → prompt: "A developer
  typed what they want to learn in a quiz and course app: "<wish>". Turn it into one topic: a short tab name (1-4
  words) and 4-8 sub-topics that cover it from the basics to what a senior professional should know." Same one-line
  reply format. The no-personal rule applies only to suggestions: a topic the user asks for is theirs.
- Parsing: lines with `|`; name trimmed of `-`/`*` bullets; sub-topics split on `;`; skip empty, "Mix" and duplicate
  names (case-insensitive); no topics at all → exception with the reply.

### Topics window (`TopicsWindow`)

720x680, Topmost, centred. "What do you want to learn?" (20 pt semibold) and an intro line; a card with one
`CheckBox` per topic (name semibold, sub-topics comma-separated below, small and faded); "Add a topic of your own": a
`TextBox` + "Add with AI" button (enabled when text is typed; Enter also adds) and a hint "e.g. "I want to learn
business regulation on PII" - Claude turns it into a topic"; Cancel and Save (accent) at the bottom.
- **First run** (`isFirstRun`): intro "Suggested from your own Claude Code chats of the last 7 days - general tech
  topics only, nothing personal. Tick the ones you want, or add your own below."; a loading overlay "Reading your
  Claude chats to suggest topics..." while `SuggestAsync` runs; suggestions start **unticked**. No chats → "No Claude
  Code chats found yet, so there is nothing to suggest. Add the topics you want below."; an error is shown in the card.
- **From the gear menu**: intro "Untick a topic to remove its tab, or add a new one below."; the current topics, ticked.
- Add with AI: disable the box, hint "Claude is shaping your topic...", then add the topic **ticked** (replacing a
  row with the same name), clear the box, hint 'Added "<name>". Add another, or Save.'; on error the hint shows it.
- Save: `Topics.Save(ticked rows in order)`, close with `DialogResult = true`. Cancel changes nothing.

## Knowledge about the user (`Knowledge.cs`)

`enum KnowledgeSource { None, File, Claude }`, saved as `"knowledge":"File"` in `settings.json` next to the exe
(default `File` when missing). `settings.json` is a flat string map shared by every setting (`AppSettings.Get/Set`;
writing one key keeps the others; an unreadable file reads as empty). `Knowledge.GetAsync()` returns the text that goes
into the question, lesson, TL;DR and discussion prompts (`LearnPath.AboutThemAsync()` wraps it as "About the learner:"):
- **File**: `profile.txt` next to the exe (empty if missing). The user writes a few lines about their role and stack.
- **Claude**: a summary of the user's own Claude Code history, built **once a day** and cached in
  `knowledge-from-claude.txt` next to the exe (reuse it if its write date is today; share one in-flight Task so
  parallel question generation builds it once; rebuild if that Task faulted).
  - `Knowledge.RecentPrompts()` (shared with topic suggestions): read
    `%USERPROFILE%\.claude\projects\<project-folder>\*.jsonl` files written in the last 7 days
    (open with `FileShare.ReadWrite`; they may be in use).
  - Each line is JSON. Keep only prompts the user typed: `type == "user"`, `origin.kind == "human"`,
    `message.content` is a **string**, `timestamp` within 7 days. Skip unparsable lines.
  - Take the newest 200, newlines flattened, each cut to 300 characters; plus the names of project folders that had
    sessions in that window.
  - Prompt: "Below are a developer's own recent prompts to an AI coding assistant (last 7 days) and the names of the
    project folders they worked in. Describe this developer for a quiz app that sets questions in their world: their
    role, languages, frameworks, databases, cloud and tools, the kind of product they build, and what they worked on
    lately. Under 150 words, plain text. Leave out secrets, credentials, people's names, customer data and anything
    else private." followed by `PROJECT FOLDERS:` and `PROMPTS (newest first):`.
- **None**: empty.

## Generating a question (`GenerateAsync(level, topic)`)

Prompt (the "About this developer" block only when the knowledge is non-empty):
```
You are quizzing a developer during a short break.
About this developer:
<knowledge>

Where it fits naturally, set the question in their stack and domain, but keep it a general lesson that is worth knowing.

Write ONE <level> question about: <topic>.
Style: <level style>.
Keep the question under 120 words. Use plain text: no markdown headings, no bold, no lists markup.
Put every code snippet in a fenced block with its language, e.g. ```java, ```sql, ```javascript, ```bash.
Short names inside a sentence go in single backticks, e.g. `HashMap`.
Then give the background theory: the concepts someone needs to know to work it out, as a hint
(under 120 words). It must not give away the answer.
Then give the answer: the key insight first, then a short explanation (under 150 words).
For a design question there may be no single right answer: give the best choice and its trade-offs.

Reply in exactly this format and nothing else:
QUESTION:
<the question>
THEORY:
<the background theory>
ANSWER:
<the answer>
```
Parse by the `QUESTION:` / `THEORY:` / `ANSWER:` markers (in that order) into `record Question(Text, Theory, Answer)`; wrong format → exception with the
raw output.

## Scoring (`ScoreAsync(question, mine)`)

Prompt: grade fairly and encouragingly but honestly (credit the key insight even if worded loosely, take points for
wrong or missing key ideas), with QUESTION, REFERENCE ANSWER, THE DEVELOPER'S ANSWER; score 0-10 and under 60 words of
feedback, plain text. Reply format `SCORE: <0-10>` then `FEEDBACK:` + text. Parse with regex `SCORE:\s*(\d+)`, clamp
0-10 → `record Score(Points, Feedback)`.

## Discussions (`ChatAsync`, `ChatAboutLessonAsync`, `ChatAboutTldrAsync`)

Three kinds, one shape. The CLI keeps no session, so every turn sends everything, split in two:
- **System prompt** (the context): a friendly senior-engineer tutor persona; the shared rules ("answer their latest
  message directly and concisely, usually under 150 words; go deeper, give examples, or correct them; when they ask
  what it means for their own work, products or platform, answer in terms of what is known about them; format lightly,
  it is rendered: short paragraphs, "- " or "1. " lists, **bold** for the key point, no headings and no tables; code in
  fenced blocks with the language, short names in backticks; when the developer attached images, read each one with
  the Read tool before answering"); the knowledge block;
  the machine notes (below); then the item:
  - **quiz**: QUESTION, REFERENCE ANSWER, THE DEVELOPER'S OWN ANSWER (or "(none)") and ITS SCORE ("N/10 - feedback" or
    "(not checked yet)"). Answer and score are read at **every turn**, so a check done after the chat opened is known.
  - **lesson**: THE LESSON (title - summary, then its text), ITS CHECK QUESTION, ITS ANSWER.
  - **TL;DR**: the whole TL;DR as text (each section title in caps with its items, then SOURCES), with its date; also
    "when it is about something recent, search the web and fetch the official source first, and name the page with its
    full https URL".
- **User turn**: "CONVERSATION SO FAR (the last DEVELOPER message is the one to answer):" + `DEVELOPER: ...` /
  `TUTOR: ...` lines + "Reply with your answer only, without a "TUTOR:" prefix."

**Run** (`RunDiscussionAsync(system, prompt)`): the developer may let Claude look at their machine, **read-only**:
- Their projects: `ClaudeProjects.Find()` (see **Save it to my Claude**) and the git repos in them
  (`ClaudeProjects.GitRepos()`: a project folder with `.git`, or a folder up to two levels below one; skip `.`-folders,
  `node_modules`, `build`, `bin`, `obj`; at most 100).
- Arguments: `-p --tools "Read,Grep,Glob,WebSearch,WebFetch,PowerShell" --settings <file>
  --disallowedTools "Write,Edit,NotebookEdit" --append-system-prompt-file <file> --no-session-persistence`, plus
  `--add-dir <folder>` for every project folder; with the **Clean** setup also `--setting-sources "" --strict-mcp-config`.
  No permission bypass: `-p` cannot ask, so anything not allowed is denied.
- The `--settings` file holds `permissions.allow`: `Read`, `Grep`, `Glob`, `WebSearch`, `WebFetch`, `PowerShell(dir:*)`,
  and per repo `PowerShell(git -C <repo> log|status|diff|show:*)` and, when it has `gradlew.bat`,
  `PowerShell(<repo>\gradlew.bat -p <repo> dependencies|dependencyInsight:*)` (also without `.bat`); `permissions.deny`:
  Write, Edit, NotebookEdit. Why per repo: `git -C <path>` and `gradlew -p <path>` take any subcommand, and Claude Code
  always asks before `cd ...; <command>`. Dozens of repos overflow a command line, hence a file.
- The system prompt also goes in a file (a TL;DR is too long for a command line). Both files are named per turn (two
  discussions can run at once) and deleted when the turn ends. Working directory: the temp folder. Timeout **10
  minutes** (a dependency report can be slow).
- Machine notes in the system prompt: "You run on the developer's own machine and may look at it, read-only: read and
  search files in their Claude Code project folders, search the web, and run only these commands -" the git form
  "exactly as: git -C <repo path as listed below> log|status|diff|show ... (never cd + git, never another subcommand)",
  `dir`, and "a Gradle dependency report, exactly as: <repo>\gradlew.bat -p <repo> dependencies|dependencyInsight ...
  (never cd first)"; "When an answer depends on their actual code, versions or setup, check it yourself instead of
  guessing or asking them to run something, and say in one line what you looked at. You cannot change anything."; then
  the project folders and the git repos, one per line.
- **Setup** (`enum ClaudeSetup { Clean, Mine }`, `"discussSetup"` in `settings.json`, default Clean): Clean leaves out
  the user's own Claude settings, hooks and MCP servers; Mine loads them like their CLI (slower).

## Ready queue (`QuestionPool`)

So questions appear instantly:
- `record PendingQuestion(Topic, Task<Question>)`. Keep **2** ready per (tab, level).
- `Take(category, level)`: dequeue if available, otherwise start one the user waits for directly; then refill.
- `FillAll(level)`: top up every tab for that level. Background generation runs at most **3 at a time**
  (`SemaphoreSlim`); a question the user is waiting for skips that limit. A random topic from `TopicsFor(level)`.
- UI thread only.

## Learn path (`LearnPath.cs`)

A course per tab, every tab except Mix. All of it is written by Claude and cached under `learn\` next to the exe
(one folder per tab, name with non-alphanumerics replaced by `-`). One in-flight Task per course / lesson; a faulted
one is retried on the next request. UI thread only.
- `record Lesson(Title, Summary)`. **Syllabus** (`learn\<tab>\syllabus.json`), written once per tab. Prompt: "You are
  designing a short course for a developer who wants to master: <tab>. It covers what every senior software engineer
  working with <tab> should know: the theory behind it and the important, practical things that matter in real systems.
  Scope (use as a guide): <the tab's topics>." + the knowledge block ("About the learner:") when non-empty + "Write
  exactly 12 lessons, ordered from the foundations to senior-level topics. Each lesson is one focused subject, e.g. for
  a browser course "cookies vs localStorage vs sessionStorage"." Reply format, one per line:
  `1. <title> | <one-sentence summary>`. Parse lines that start with a number, a dot and have a `|`.
- `record LessonContent(Text, Check, Answer)`. **Lesson** (`learn\<tab>\lesson-NN.json`), written when first opened.
  Prompt: "You are teaching lesson N of a <tab> course for developers growing into senior engineers." + knowledge
  block + the numbered course list + "This lesson: <title> - <summary>" + "Teach it in under 600 words: the theory: what
  it is, how it works underneath, and why it is designed that way; real examples where they apply (real code, commands,
  configuration or a realistic production scenario); what a senior engineer must know: trade-offs, common mistakes and
  pitfalls. Plain text with short paragraphs; you may use simple "- " bullets. No markdown headings and no bold." + the
  fenced-code / backtick rules + "Then write one short question that checks the key idea of the lesson, and its answer
  (under 80 words)." Reply format `LESSON:` / `CHECK:` / `ANSWER:`.
- **Progress**: `learn\progress.json`, `{ "<tab>": [done lesson indexes] }`.
- **Prepared ahead** so opening a course or carrying on is instant: `PrepareAll()` on tray start writes every course's
  lesson list and its next lesson not done yet (already written ones are read from disk); `PrepareAsync(tab)` runs
  again after **Mark as done** to get the next lesson ready. At most **3** courses prepare at a time (`SemaphoreSlim`);
  failures are swallowed there and shown/retried when the user opens that course or lesson.

## TL;DR (`Tldr.cs`)

A daily briefing per tab (every tab except Mix), written by Claude **from the web** (`RunClaudeAsync(prompt, web:
true)`), cached as `tldr\<tab>.json` next to the exe (name with non-alphanumerics replaced by `-`). UI thread only;
one in-flight Task per tab, a faulted one is retried.
- `record TldrSection(Title, Text)`, `record TldrSource(Title, Url)`, `record TldrContent(Written, Sections, Sources?,
  Format = 0)` with `CurrentFormat = 2`. A saved TL;DR is **old** - written again - when it is a day old, has no sources
  or an older format. `GetAsync(tab, refresh)` reads it from disk while not old, else writes it.
- Prompt: "You are writing a TL;DR briefing on <tab> for a developer growing into a senior engineer. Scope (use as a
  guide): <topics>." + knowledge block + "Today is <yyyy-MM-dd>. First search the web and fetch the official sources
  (release notes, changelogs, official blogs and docs) to get the latest, current data. Do not rely on memory for
  anything recent, and give version numbers and dates." + five sections, 3 or 4 items each: LATEST RELEASES (headline
  with version and date), HOT TOPICS, INTERESTING QUIRKS, WHAT A SENIOR MUST KNOW, OPTIMIZATION TIPS. Every item, each
  line 1-3 sentences: `* <short headline>`, `Context:` (the background - the problem or the situation before), `Why:`
  (why they did it / why it works this way), `Good for:` (what it gives in practice, with a concrete example or
  snippet), `For you:` (what it means for the learner's own work and products; "Not directly relevant to your stack."
  when it does not apply - never invent a link; left out when nothing is known about the learner). Under 2000 words.
  Then `SOURCES:` every page used, one per line `- <page title> | <full https URL>`. Plain text, the code rules.
  Reply format: each title alone on its line with a colon, followed by its items, then SOURCES.
- Parse each section between its title and the next; any title missing → exception with the reply. Section titles are
  stored capitalized ("Latest releases"). Sources: keep only absolute http/https URLs (they open in the browser).
- `PrepareAll()`: every tab's TL;DR in the background, **2 at a time** (`SemaphoreSlim`), on tray start and on
  `Topics.Changed`; failures are left for when the tab is opened.

### TL;DR view (`TldrView`)

- Topic chips (`ChipList`) per tab; a header card: "fresh from the web" (hand note), the tab name, "UPDATED <date> ·
  N SOURCES", **Refresh** (rewrites now) and **Discuss** (enabled when a TL;DR is shown).
- **Sub-tabs** in the mode-tab style: Latest releases · Hot topics · Quirks · Senior must-know · Optimization ·
  Sources (N). The open sub-tab stays when another tab is picked.
- A section: a numbered eyebrow ("01 · LATEST RELEASES"), then per item a block with a coloured bar on the left (one
  accent per section), the headline (display font) with a small **+ my Claude** button after it, and its lines, each
  under a small mono label (CONTEXT, WHY, GOOD FOR); FOR YOU stands out on a violet tint. A section written without
  `* ` items is shown as it is. Sources: one line per page, a link (opens in the browser) and its host.
- Loading overlay "Claude is reading the latest on <tab> online..."; errors shown in its place. A version counter
  drops slow replies for a tab no longer selected. Opens its first tab only when the view is first shown.

## Save it to my Claude (`ClaudeProjects.cs`, `SharePanel`)

- **The user's projects**, found on the machine - nothing hard-coded: every folder in `%USERPROFILE%\.claude\projects`
  (or `DEVBREAK_CLAUDE_PROJECTS`, a sandbox for tests and demos); its real path is the `cwd` recorded in its newest
  session logs (`*.jsonl`, first 60 lines, opened with `FileShare.ReadWrite`); keep folders that exist, skip the temp
  folder and the home folder, no duplicates. A short **fingerprint** per folder: its first 24 top-level entries (not
  `.`-names) and the start of its `CLAUDE.md` or `README.md` (4 non-empty lines, 300 characters).
- **+ my Claude** on a TL;DR item opens the `SharePanel` beside the TL;DR (the same side panel as a discussion):
  "save it to your Claude" (hand note), the headline, a loading overlay "Claude is matching it to your projects...".
  `SuggestAsync(tab, item, sources)` (no tools): the item, the TL;DR's sources, the numbered projects with their
  fingerprints and the knowledge block; "Pick the projects this item is really useful for - at most 3, and none when it
  does not fit any of them. For each, choose: memory - a fact, change or gotcha Claude should remember when working in
  that project (most items); skill - only when the item is a procedure a developer would repeat there." Content for that
  project, with the source URL, today's date and a closing line to check it is still current; memory under 120 words,
  skill numbered steps under 300 words. Reply blocks `TARGET: <n> | <memory|skill> | <kebab-name> | <description>`,
  the content, `END` - or the single word `NONE`.
- Each suggestion: a ticked checkbox with a MEMORY / SKILL badge and the folder, "<name> - <description>", the content
  in an editable box. **Save selected** writes only the ticked ones; "Nothing is saved until you press Save." until then.
  - memory → `<projects>\<key>\memory\<name>.md` with front matter (`name`, `description`, `metadata: type:
    reference`) and the content, plus a line `- [<name>](<file>) — <description>` appended to that folder's `MEMORY.md`;
  - skill → `<project>\.claude\skills\<name>\SKILL.md` with front matter (`name`, `description`).
  Never overwrite: a taken name gets `-2`, `-3`... The status shows the saved paths.

## Sessions (`ClaudeSessions.cs`, `SessionsView`)

The user's own Claude Code, inside Dev break: real sessions - the same ones the CLI keeps under `.claude\projects` -
started in a folder or continued, worked in like the CLI, and continuable with `claude --resume <id>` in a terminal.
- **List**: every `<projects>\*\*.jsonl`, newest first, the first 60 whose folder (the first `cwd` in the file) still
  exists and is not under the temp folder. Title: the last `ai-title` / `custom-title` line (read from the last 256 KB),
  else the first prompt the user typed (`type == "user"`, string content, `origin.kind == "human"` or no origin, not
  starting with `<`), else the folder name. Read with `FileShare.ReadWrite | Delete` (sessions may be in use).
- **Transcript** of a session: its lines in order, skipping `isSidechain` and `isMeta`: the user's typed prompts, and
  each assistant message's `text` blocks and `tool_use` blocks (shown as a step: the tool name and its `command`,
  `file_path`, `pattern`, `url`, `query`, `description`, `prompt` or `skill`, 140 characters). The last 300 entries.
  A typed prompt is a string or text blocks (messages written as stream-json); a user line holding a `tool_result` or
  "[Request interrupted ..." is not one. A "/command" saved as tags shows as "/name args" (`<command-name>`,
  `<command-args>`, in either order with `<command-message>`), its `<local-command-stdout>` / `-stderr>` - in a user
  line, or in newer files a `system` line with `subtype: local_command` - as the turn's answer; `<local-command-caveat>`
  lines are left out. A message starting with "[I ran: " blocks shows them as shell blocks (below). The branches cut by
  a conversation rewind made here are skipped: from the line with the cut message's uuid until a user line whose
  `parentUuid` is where the session resumed (kept in `session-settings.json`; the file keeps both branches - measured,
  following `parentUuid` chains instead drops lines in 14 of 60 sessions that were never rewound, so it is not used).
- **A session's process** (`SessionProcess`): one kept-open `claude -p --input-format stream-json --output-format
  stream-json --verbose --permission-prompt-tool stdio --replay-user-messages --permission-mode <mode> [--model m]
  [--effort e]` and `--session-id <new id>` for a new session or `--resume <id>` (`--resume-session-at <uuid>` after a
  conversation rewind; `--resume <from> --fork-session --session-id <new id>` for a branch), working directory = the
  session's folder, env `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1`. First written: the `initialize` control request.
  No `--setting-sources`: the user's full setup loads (CLAUDE.md, memory, skills, plugins, hooks, MCP servers). Each
  message is a stream-json user line; the turn ends at its `result` line. Its output is read all the time (questions
  and events come between steps too). Started when the session has none, it ended, the model or effort was changed,
  or the session file changed since the process last wrote it (size or write time against a stamp taken at the turn's
  end and 4 s later - the session was used in a terminal; two writers would split its history; measured: the next
  turn then knows what was said in the terminal). Closed after 10 minutes idle (checked every minute) and with the app.
  Measured: later turns of an open process 1.2-3.6 s, the first 11-14 s. A turn's cost is the difference of the
  process's `total_cost_usd`, which is a running total (0.0047, 0.0101, 0.0106 over three turns) that a resumed process
  carries on from the session file's last `cost-state` `totalCostUSD` (a total below it: counted from 0). Control
  requests used (each measured): `interrupt`, `set_permission_mode`, `set_model`, `get_context_usage`,
  `side_question`, `rename_session`, `rewind_files`, `stop_task`; the CLI's `can_use_tool` requests become cards;
  any other request from the CLI is answered with an error so it does not wait.

### Watching the turn, learning from it (`TurnLog`, `Watch`, `SessionPane.Coach/Quality/Lessons`, `SessionLessons`, `SessionStats`)

Measured on the author's own sessions (30 days, 119 h of turns): about a third of the time was waiting on builds,
deploys and background tasks, 5% of tool calls failed, the same command families were worked out again in 20-30
sessions, and about one turn in ten was interrupted or corrected. So a pane watches its turn, checks the result and
keeps what went wrong as a lesson - nothing blocks or slows a turn, and nothing is written without a click.
- `TurnLog`: the process's every stream line (`SessionProcess.Line`) gives each tool call its start, end, error and
  result (300 characters), a shell command its family (`KeyOf`: the first two words after a leading `cd ... &&`), the
  files Edit/Write changed and how many lines; a subagent's steps (`parent_tool_use_id`) are logged but are not the
  turn's own work.
- Waits: while a shell command runs, the footer shows `⧗ waiting on <command> · m:ss · usually ~N min` - "usually" is
  the median of that family in the user's own sessions (3+ runs). When the window is not in front, a long wait (usual
  over 2 min, or a background task with nothing else running) gives a tray balloon once, and a second when Claude
  needs the user again (the turn ended, a card, a coach flag). The answer-shape note also says: run long commands in
  the background, never wait in a sleep loop.
- The coach (`Watch.Flag`, checked every 2 s): the same call failing 3 times in a row; the same call 4 times; 5 of the
  last 10 calls failed; an error from a command written for another shell; no new step for 5 minutes with nothing
  running; 12 steps without progress (no file written, no new result, no new error). On turns past 2 minutes, a Haiku
  check once a minute (only when steps grew, at most 10, footer toggle **AI check**) answers `on track` or
  `drifting: why` + `nudge: ...`; an answer for a turn that ended meanwhile is dropped. A flag is a card above the
  box: the reason, the last 5 steps, an editable nudge, **Send nudge** (into the running turn), **Think differently**
  (Haiku proposes 2-3 other approaches; a click puts one in the nudge), **Fresh start** (stop, rewind the conversation
  to before the turn, the message back in the box with "What did not work last time: ..."), **Dismiss** (not again
  this turn). A turn of 2+ minutes ends with `⏱ waiting m:ss · tools m:ss · model m:ss` and, when one stands out, the
  biggest saving (a foreground command of 2+ minutes, a family that failed 3+ times).
- Quality: a turn that changed files and says done / fixed / works / passes / implemented / ready / all set with no
  check after the last change (a build, a test runner, a localhost call, a changed file run, a browser tool) gets the
  coach card "Claims done, not verified after the last change" with a nudge naming the check for its files. The done
  line of a turn that changed files has **review** (**⚑ review suggested** past 3 files or 150 lines): a separate
  clean claude in the folder with Read/Grep/Glob, the ask, the file list and `git diff` (60,000 characters; none
  outside a repo), asked for real defects only as `path:line - problem - why`; its card has **Send to Claude** and
  **Dismiss**. A turn of 5+ steps is graded after it ends (Haiku, footer **Grade** with its menu: on/off and the user's
  own rubric file appended to the built-in one, `Rubric.cs`): the ending's claims against the record of calls, as a
  JSON array; the line `✓ graded: clean` / `⚠ graded: N issues` (click: the criteria and evidence) / `grade
  unavailable`. The same criterion broken in 3 graded turns of a folder becomes a rule lesson.
- Lessons: after a turn with 2+ failed calls that later worked, a next message that corrects it, or a stopped turn
  asked again, the user's default model drafts 0-2 lessons (memory, skill or rule; the folder's dismissed ones with
  their reasons are in the prompt). A card under the turn: **Save** (memory → the folder's project memory as the CLI
  reports it, with its `MEMORY.md` line, the Factory's writer; skill → `~/.claude/skills/<name>/SKILL.md`; rule → the
  end of `~/.claude/CLAUDE.md`), **Edit...** and **Dismiss...** (with a reason) in the panel above the box - a text box
  inside the read-only transcript takes no keys. A saved lesson can be undone (the file and index line, the skill
  folder, the appended text). Kept in `session-lessons.json` next to the exe with the per-folder grade counts.
- Effort hint: a message of up to 80 characters with commit / push / merge / restart / rebuild / deploy / run /
  status / pull / rebase / tag, effort not low: "A quick step · **Effort low** would answer faster"; the link sets low
  until changed (effort restarts the process, about 12 s, so not "for one message").
- `SessionStats` reads `~/.claude/projects` (files of the last 5 weeks; terminal, desktop and `-p` sessions; not the
  automated "You are grading..." kind) with the audit's rules: active time from `turn_duration` (else gaps under 15

  access"), a filter box, **Refresh** and **Back to chat**; sub-tabs **Memory · Skills · Plugins · MCP servers ·
  Agents** with counts; a list (name, description or source; MCP status as a chip: connected lime, needs-auth coral)
  and the selected item on the right: its source, status and file, its text without front matter (markdown files
  rendered with soft wraps), **Open file**, and for a skill **Use in this session** (puts `/<skill> ` in the
  message box and goes back to the chat - a skill runs from `-p` that way). MCP items explain their status.

## Factory (`Factory.cs`, `FactoryView`)

A software factory: a task goes from its source to a **draft pull request**, and what the run learned goes into the
repo's Claude harness. Runs are kept in `factory.json` next to the exe (git-ignored with the rest of the user data).
- **A task**: **Typed** (what to build or fix), **Jira** (an issue key) or **Spec doc** (a file path or a link;
  Browse... picks a file); a **folder** - the repo, or any folder with repos somewhere in it (an editable list of
  `ClaudeProjects.GitRepos()`, or Browse...; the last one is remembered) - the **base branch** (for a repo: its
  current branch; empty: the located repo's current branch) and an optional **verify command** (remembered per repo;
  empty: Claude proposes one). **Start run**.
- **The run**, each step logged:
  0. **Locate**: the repo the folder is in (`git rev-parse --show-toplevel`); else the git repos up to 3 levels below
     it (`.git` folder, or file for a worktree): none stops the run, one is it, several - a `claude -p` reads the
     task and the repos' fingerprints and ends with `REPO: <number>` or `REPO: NONE <why>`. It also gets up to 20
     earlier runs in the same folder (their task, the repo each went to) and may answer from them without searching
     (before, every run searched all the repos; with them round 6 picked with 0 tool calls). For a typed task it has
     only `Read,Grep,Glob` (read-only, enforced); a Jira issue or a spec needs the machine's own tools to be read, so
     it gets the developer's setup with bypass minus `Edit`, `Write`, `NotebookEdit` and the publish denies (the
     shell can still change files - the same access the plan turn has). Then the base branch and the remembered verify command for it.
  1. **Workspace - always the developer's own checkout, never a worktree** (no copy: its dependencies and build output
     are already there, and what runs locally is served from it; a worktree is a second copy of the files - 603 MB with
     a fresh `npm ci` in a measured run - whose work had to be merged back by hand). **Until there is a change to build
     the run only reads the checkout as it is** - the developer's branch and uncommitted work, nothing switched, no lock
     (the plan, research and answer sessions are told so, and to change, switch, stash or commit nothing): research and
     answers never change a file, and switching for them once pulled the branch from under a session editing there.
     The workspace step below runs when the build starts. **A session working in the repo first gets to finish**: any
     Claude session transcript (Dev break's or a terminal's, not the run's own) that edited a file in the repo, or ran a
     command that goes into it (cd, pushd, Set-Location, git -C - not one that only loads a file from it), in the last
     10 minutes makes the run wait ("Waiting: a Claude session (<id>) edited <file> at <time> ..."); it re-reads the
     transcripts every 30 s, goes on by itself when they are quiet, and **Take it anyway** goes on at once. Stop ends
     the wait. Then the base commit is read again (the session may have committed). The run checks the checkout can be used
     and **asks when it cannot** (stops at Needs you with the question): another run working in it ("... Wait for it
     and press Continue.") or git cannot read it. Then it notes the branch the checkout is on (or its commit when
     detached), `git switch -c devbreak/<slug>-<id> <base commit>` (or `git switch` to it when the branch exists) and
     works there. **The developer's own local changes do not block it** (temp files, local settings - modified,
     staged or untracked): their paths are noted with a SHA-256 fingerprint of the content, a snapshot of them is taken
     with `git stash create` (nothing in the checkout changes), and they are logged ("Your N local changes stay in place
     ..."); the switch carries them along untouched. They are never committed: "did the run change
     anything" and "is its work committed" count only the run's own changes (a noted file counts only once its
     content differs); the review diff is `git diff <base> -- . :(exclude,literal)<each local file>` with the run's new
     files marked `--intent-to-add -- :(literal)<file>` (no `git add -A`, so the developer's index is untouched;
     literal, because a plain pathspec is a glob: excluding `f[1].txt` also hid `f1.txt` from the reviewer in a test); the PR step is told the files
     and to stage only the change's files by name. **On a conflict the developer's changes are stashed, not the run
     stopped.** Before verify and before the PR, a local change whose content differs (the run edited that file): the
     run's edits alone are worked out with `git merge-file --object-id <branch blob> <their blob from the snapshot>
     <the file now>`, their version is put back (`git restore --source=<snapshot>`) and stashed by path (`git stash
     push -m "devbreak <id>: your local changes in N files the run needed" -- <files>`), and the merged file is
     written (`git cat-file --filters`, so line endings stay); the files leave the local list and are logged. Only an
     overlapping edit (merge-file reports conflicts) or a file that was not in git stops the run and asks. A switch git
     refuses ("would be overwritten by checkout") stashes all local changes (`git stash push --include-untracked -m
     "devbreak <id>: your local changes, stashed to switch to <branch>"`), notes them again and switches. When a run (or its continue, feedback, PR anyway)
     is done, the checkout goes back to that branch - local changes carried along - if the run's own work is
     committed; otherwise it stays on the run's branch and the run says so. Continue, feedback and PR anyway first
     switch the checkout to the run's branch.
     Old records with a separate worktree still show and clean up; no new run makes one.
  2. **Plan**: a new Claude Code session in the repo folder (as in Sessions: full setup, bypass) reads the task - Jira
     and spec with the tools on the machine - first understands the mission with the machine's skills, MCP servers
     and tools (running the app or its services, reading logs or data, inspecting or debugging a running service),
     learns how the repo is built, run and tested and how the change can be seen in the running app, and replies `TITLE:`, numbered steps and, when no verify command was
     given, `VERIFY: <command>`; `CANNOT_READ: <why>` stops the run.
     **Questions**: when the task leaves a decision that is the developer's (behaviour, naming, defaults, which of
     several options), the plan adds `QUESTIONS:` with numbered questions and suggested answers, and the run **stops
     before building** ("The plan has questions for you. Answer them in the box below and press Send to the run (or
     press Continue to go with the suggested answers)"). Answers sent to the run update the plan in its session (more
     questions stop it again), then it builds; Continue builds with the suggested answers.
     **Every turn** is told to change files only inside its folder - never shared build homes (Gradle, Maven, npm,
     Ivy settings), the developer's profile, tool or system settings, not even to make a command work - and to end
     with `NEEDS_YOU: <what, where, why>` instead; that line stops the run with "Claude needs you: ...".
  3. **Build**: the same session implements the plan and its tests, without committing or pushing, and without
     starting the app or calling it - Prove runs the app once (seen in a real run: Build restarted the service, 41 s,
     and Prove restarted it again, 40 s).
     The session's turns share **one open claude process** (`claude -p --input-format stream-json`, each turn one
     user message, ending at the turn's `result` line) while the folder, session id and arguments stay the same; a
     turn that needs other arguments (the PR turn, which may push) gets a new one and the old one is ended first.
     A new process starts the developer's whole setup each time: measured 11.7-13.7 s for a one-line answer, against
     2.9-3.0 s for a later turn of an open process. **The handshake, as the Agent SDK does it**: claude reads stdin
     only once it is initialized, so the first thing written is `{"type":"control_request","request_id":...,
     "request":{"subtype":"initialize"}}`, and the message goes in only after its `control_response` (60 s at most,
     else the turn fails "did not answer its initialize request"). Without it, a message bigger than the pipe's buffer
     blocks the writer and the run hangs before its first tool (seen twice; in a test 6,000- and 20,000-character
     messages blocked without it and 6,000/20,000/50,000 went through with it; the 3,207-character task that hung ran
     to the end with it). A stopped or failed turn ends the process, and so does the end of the run's drive.
  4. **Verify**: Dev break runs the verify command itself (a fresh PowerShell in the run's folder with the machine's
     default environment, both streams, 30 min max - so the plan's command must carry what its own commands needed,
     e.g. `$env:JAVA_HOME=...`). It is done when the command's own process exits (the `Exited` event), not when every
     holder of its output pipe has closed it - a build daemon the command starts inherits the pipe and lives for hours
     (that hung a verify; measured 11.4 s against 0.5 s for a 12 s child). The plan chooses the command **by regression
     risk**, not the whole suite by habit: compile everything and really run (no build-cache result) the tests that
     cover the changed code and the code that uses it (found by its usages), naming them and saying in one line why
     that is the scope; the full suite only when shared code many places use changes. A command used in the repo
     before is passed as a hint (its environment and flags), not reused as it is; one the developer typed is used as
     it is; on failure the session fixes it (the code, not the test) and it runs again, up to 3
     fixes. When the cause is the command or its environment, the fix ends with `VERIFY: <corrected command>`: Dev
     break uses it from then on and remembers it for the repo (seen in a real run: the default JDK 17 could not start
     a build that needs JDK 25, and without this the session changed a shared Gradle home to get around it). No changed files stops
     the run.
  4b. **Prove**: the session proves the change - starts the app and the services it needs with the machine's skills,
     MCP servers and tools, from the worktree; exercises what the task changed; stops what it started - and produces
     **the proof the plan chose** for this feature. The plan ends with `EVIDENCE: <kinds>` from **screenshots** (the
     running app at the sizes that matter, a "before" taken before the change when it helps - never in a worktree),
     **video** (a short recording of the interaction), **red-green** (the new tests fail without the change and pass
     with it, both outputs), **coverage** (of the changed lines, with the uncovered ones), **mutation** (scoped to the
     changed files - the score and surviving mutants), **crap** (complexity and coverage of the changed methods),
     **api**, **logs**, **trace**, **perf**, **other** - the repo's own tools first, a missing one run without adding
     it to the repo's dependencies, a kind that cannot be produced marked skipped with why, never invented. What the
     task asked to be handed back (a curl to try it, an answer, a link) comes after a `RESULT:` line, checked, and is
     kept as the run's **Result** - shown in a box on top of the run with the PR link and Copy, and put in the PR. The files
     go into `<traces>\<id>-proof` (not the repo) with a manifest `evidence.json`: one entry per piece -
     `kind`, `file`, `proves`, `result` (pass / fail / skipped), `detail`. The turn ends `PROOF: PASS`, `PROOF: FAIL
     <what>` or `PROOF: SKIPPED <why>`. Dev break reads the manifest and logs it with the planned kinds not produced.
     FAIL goes back to the session to fix, then verify and prove again, up to 3 fixes; no PROOF line stops the run.
     When the task names sources to check with (a database, a bucket, a running client, a URL, an MCP server), the
     prompt has each used with fresh calls - not an earlier run's logs - with one evidence entry per source, a source
     that cannot be used getting a `skipped` entry with the reason (a run once skipped a bucket and a client the task
     named). The answer of a no-change task is done only on an explicit `PROOF: PASS` or `SKIPPED` (the note says what
     was not checked): no PROOF line is not a pass - the second attempt is told so and asked for the check.
     **Open evidence** opens the folder.
  5. **Review**: a fresh `claude -p` that can only read (`--tools Read,Grep,Glob`) gets the task, the plan, the
     diff against the base commit and **the evidence** - the verify command's exit code and output end (run by Dev
     break on that worktree), the proof planned, the manifest (and what was planned but not produced) and the app
     check - and is told to judge it rather than ask for runs it cannot do, weak or missing proof being a real
     problem; it
     replies `VERDICT: PASS` or `FIX` with findings; FIX goes back to the session, then verify, prove and review
     again, up to 2 review rounds.
  6. **Draft PR**: only now may the session publish - until here every turn runs with `--disallowedTools` for
     `git push` and `gh pr create` (Bash and PowerShell). **Not watertight**: the rule matches the command's start,
     so `git -c user.name=x commit ...` got through in a test (a commit was made) - the same holds for `git push`.
     Hence the checks in code below. In three steps:
     - **Commit** (still no push): the session commits the change's files.
     - **Dev break checks the commit**: the folder is on the run's branch, and `git diff --name-only <base>..HEAD`
       holds none of the developer's local-change files (else the run stops, nothing pushed, with how to take them out)
       and at least one file; logged "Checked the commit <sha>: N files of the change, none of your local files".
     - **Push and PR**, with commit, add, reset, rebase, cherry-pick, merge, stash, checkout, switch, restore, rm and mv
       disallowed: the session pushes exactly the checked commit (`git push origin <sha>:refs/heads/<branch>`) - the
       developer's own PR hooks still see the push - and opens the PR. After it, the remote branch must be at the
       checked commit (`git ls-remote`), else the run stops at Needs you (fail closed), the PR link kept.
     It opens a draft PR into the base with the machine's own tools (any host) - the git host's official MCP server
     first when one is connected and signed in (Atlassian's for Bitbucket, GitHub's for GitHub), else its CLI or tools,
     saying which it used - the description saying how it was
     verified (and the app check, describing its evidence without committing it; the app is not run again unless
     a check on the machine requires it), linked to the Jira issue; the PR is the URL on the reply's **last line**
     only (a link elsewhere in the reply is not a PR).
  7. **Learn** (after every run that got a worktree, unless stopped): a `claude -p` without tools reads the task, the
     log, the repo's `MEMORY.md` and the factory's rules and skill names for the repo, and replies
     `LESSON: <memory|claude-md|hook|skill> | <name> | <description>` blocks (at most 4). It is asked first for what the
     next run there needs most: the fastest way to build, start, restart and check the service (commands, ports, health
     URL, environment), where the logic for that kind of task lives and the repo's conventions, and the language and
     framework facts the run had to look up. A fact about a state that can change (access, a login, a connector, a
     running service, a machine setting) ends "Checked on <date> - re-check before relying on it", and the plan
     prompt says to re-check such a note with one quick call when the plan depends on it (a run once kept "the
     connectors are not authorised" and the next one skipped them after they were signed in). **Memory** notes are saved at once into the repo's memory folder (from the
     init line), listed in `MEMORY.md`, ending "Learned by a Dev break factory run on <date> (<title>)" - **Undo**
     removes the file and its line. **Rules wait for the developer**, and never go into the repo (a file there would
     leave the run's checkout dirty and could end up in a PR; seen in a real run): they go to
     `factory-knowledge\<repo path as a name>\` next to the app - **Apply** appends a rule line to `rules.md`, saves a
     skill to `plugin\skills\<name>\SKILL.md` (the folder is a plugin, `plugin\.claude-plugin\plugin.json`), or merges
     a hook object into `settings.json`. Every turn of a run in that repo gets them: `--append-system-prompt-file
     rules.md`, `--plugin-dir plugin`, `--settings settings.json` (each proven headless: the rule, the skill and a
     UserPromptSubmit hook's context all reached Claude); **Dismiss** drops it.
  Anything that stops a run (a failed turn, checks still failing, no PR URL) ends it at **Needs you** with the reason;
  **Stop** ends it at **Stopped**. A run open when Dev break closes is marked Stopped on the next start.
- **Autonomous** (a checkbox in the form, on by default, remembered): no human in the loop.
  - The plan's questions take the suggested answers - "no one will answer, so make them the best choice" - logged as
    "Decisions taken on my own" and listed in the PR description.
  - Every turn may change what the work needs outside its folder (local machine settings, a shared build home, a local
    service's config): each file copied to `<file>.bak-devbreak` first and reported as `OUTSIDE: <path> - <what> -
    <backup>`, logged and listed in the PR; never secrets, credentials or logins. `NEEDS_YOU:` is only for what no tool
    can do (a login in a browser, a credential, an access grant).
  - Another run working in the checkout: this one waits for it (Needs you, then Continue) - never a separate worktree.
  - A Claude session working in the repo when the run would switch it: the run waits for it (Take it anyway to go on).
  - Stuck on its checks (verify, prove or review still failing): one **fresh attempt** - a new session plans again with
    what went wrong (the note, the last verify, review findings and app check), builds, checks, PR. Stuck again, or
    NEEDS_YOU: it stops - the developer is told by a Windows notification - and Learn is asked what would have let it
    finish on its own ("THE RUN GOT STUCK ..."), so the next run corrects itself. A run that stops on NEEDS_YOU inside
    a step learns too, once it got as far as a Claude step (seen in a test: it skipped Learn).
  - Learned rules (rule lines, skills, hooks) are applied at once, each with **Undo** (the appended text taken
    out, the skill's folder deleted, the settings restored from the backup made before).
  Not autonomous: the questions stop the run, outside changes are forbidden (`NEEDS_YOU`), rules wait for Apply.
- **Departments** (`FactoryDepartment`: Development, Troubleshooting, Research, Management; pills at the top of New
  task, remembered as `factoryDepartment`; shown in the History row when not Development). **Auto** (the default) leaves
  it to **the gate** (`RouteAsync`, the first step of the run): a `claude -p` (no tools for a typed task; for Jira or a
  spec the machine's tools minus editing and publishing) reads the item against the four departments' descriptions
  and replies `DEPARTMENT: <name> - <reason>`; logged "Gate: <name> - <reason>"; a problem with an unknown cause goes
  to Troubleshooting, a known one to Development (tested: a support-worded case, a question, a feature and a strategy
  item each went to the right one). **Development** - the pipeline above. **Troubleshooting** and **Research**
  change no code: no verify command (the box is disabled), the report always on (ticked and disabled), and the plan
  step is an investigation (`InvestigateAsync`, span "Diagnose" / "Research") that always sets `NoChange` and goes to
  the checked answer. Troubleshooting is told: reproduce it as reported and say what the customer sees; find a
  control that works and compare; find the root cause (file:line, data row or setting), proven apart from
  suspected; say the fix, where, and who makes it. Its check reproduces again live and shows the control working,
  and its `RESULT:` is in the call-center order (what the customer sees, why in plain words, what to tell them and a
  workaround, the root cause, the fix and who, not verified); its report opens with a plain "For the call center"
  part, then "Technical". **Fix it (Development)** on a done troubleshooting run creates a Development run in the same
  repo and base whose task is the diagnosis (`HandOff`). Research is told to answer from the code, the running app
  and the data, each claim backed by a file:line, a call or a row. **Management** (step "Brief"): what is asked and why
  it matters; where the company stands (sourced facts from the code, systems, data and documents, and the market from
  the web, with links); 2-4 options with value, effort, risk and needs; a recommendation with first steps by
  department and the open questions for management - estimates kept apart from facts. Its check re-checks each fact
  against its source; its `RESULT:` is the brief in decision order; its report opens with an "Executive summary"
  (the recommendation, the decision asked, value, cost, top risk), then the options as a table.
  **Folder-wide**: when "Pick the repo" answers `REPO: NONE` for a department other than Development, the run works in
  the folder itself (`FolderWide`, `Worktree = Folder`, no branch, no workspace step) and its knowledge and memory live
  under the folder (`Home`). Turns of every department but Development also deny git's writing commands (commit, add,
  reset, rebase, cherry-pick, merge, stash, checkout, switch, restore, rm, mv - the same prefix rules as the PR step,
  with the same weakness against `git -c ...`).
- **The department manager** (`ManageAsync`, autonomous runs only): when a drive ends at Needs you, before Learn, a
  `claude -p` with the developer's setup and bypass (publishing denied, the factory's knowledge in) in the run's
  folder gets the task, why it stopped and the last 14 log entries, and ends with `DECISION: RESUME <what it did>` -
  allowed at most twice per run (`ManagerResumes`); the run is continued from where it stopped after the drive ends
  - or `DECISION: ESCALATE <what the human must do>`: `ManagerCase` (what to do, why it stopped, proposed factory
  changes) is shown in a coral **"Needs a human"** box on the run, the note becomes "Needs a human: ...", and the
  Windows notification is titled "Dev break factory - needs a human". `RULE:` lines are applied like Learn's rules
  (autonomous: at once, with Undo), `FACTORY_FIX:` lines are kept in `FactoryFixes` for a human to approve (never
  applied), `OUTSIDE:` lines are listed. No decision counts as escalate. A resumed run learns when it ends.
- Files under `.claude/` in the developer's local changes (Claude tooling state - a hook's edit log grows with every
  edit) never stop a run when they change (seen: `.claude/session-changes.log` stopped a run that never touched it);
  they stay in the local-changes set, so the commit check still keeps them out of every commit.
- **Hardening (after a diagnosis of a day's runs and research into Devin, Factory, OpenHands, Copilot's agent, Jules,
  Codex, Cursor and others):**
  - **Prove once, after the review is clean** (as Devin records proof only after green): checks are verify, then
    review (told the app check comes after it, so it judges the code, tests and verify output and does not count the
    missing proof), fixes and re-review up to the cap; then the app check once. A fix the app check needed gets one
    more review with the evidence. (Before: prove after every review fix - 47 minutes over 8 attempts in one run.)
  - **Continue carries what stopped it**: the reviewer's open findings, the failing verify output or the last app
    check go into the continue turn (a continue that saw only the one-line note changed nothing, and the same finding
    came back).
  - **Stuck detection** (OpenHands' thresholds): the same finished tool call 4 times in a row, or the same call failing
    3 times in a row, cancels the turn ("The turn was stuck: ...") and the manager takes it.
  - **The manager decides in 5 minutes** (`ManagerBudget`) and is told never to search whole drives, build caches or
    node_modules; out of time, it escalates (one spent 12 minutes on a find over the Gradle and Ivy caches).
  - **No false asks**: every file path a NEEDS_YOU names is checked on disk; missing ones are flagged in the message
    (a run once asked the developer to paste a file it never wrote).
  - **Edits the developer's tooling sees**: every turn is told to change files with Edit and Write, never scripts in
    the shell (the developer's PR gate counts Edit/Write calls and blocked a run that edited through python).
  - **Secret scan before the push** (as Copilot's agent): the lines the commit adds are matched against private keys,
    AWS, Google, GitHub and Slack tokens and password/key/token literals; a hit stops the run before anything leaves
    the machine; Continue on that stop accepts exactly those findings (`SecretsAccepted`). Tested: 4 of 4 caught, the
    env-variable and `${...}` lines not.
  - **The command guard**: a PreToolUse hook (`factory-guard\guard.ps1`, passed with the learned hooks in one
    `--settings`) reads the whole command with options before the subcommand stripped, and the git tools of MCP
    servers, and refuses by mode - nopublish (push, gh pr create, PR tools), frozen (git's writing commands), all
    (both, for troubleshooting, research, management). It closes the `git -c ... commit` hole of the prefix rules
    (tested: blocked, `git -C . status` allowed; 7 of 7 sample calls right).
  - **Linked runs in order**: the run lists other repos in dependency order (a library before what uses it); they run
    one after another and the parent waits for them before its own checks (before: in parallel - a proof passed before
    its backend existed, and a run restarted a service another was proving against).
  - **One run per checkout across Dev breaks**: a lock file `.git\devbreak-run.lock` (pid, app folder, run, title),
    taken when a run works in the checkout and freed when its drive ends; a live lock of another run makes the
    checkout busy (autonomous too); a dead holder is free. `Busy` is saved with the run while it is
    driven (also during Learn and the manager), and a restart marks a busy run stopped.
  - **Proof scripts kept**: each repo has `factory-knowledge\<repo>\proof-scripts`; prove and answer checks are told
    to reuse and adapt those and save new ones there, and to keep evidence to the manifest and about 15 files.
  - Troubleshooting, research and management never reach a build path from feedback. One with no answer yet takes
    the reply into its investigation: the replies go into the investigation prompt ("The developer replied while this
    waited - follow it; it overrides what was assumed before") and it works the answer out again (before: "no answer
    yet to revise - press Continue", and only the manager got the task going).
  - **Code-only questions are checked in the code** (`CodeOnlyCheck`, on the research answer check): re-read every
    cited file:line and the callers named; run something only when quick and it adds proof; a learned rule for the repo
    comes first (one answer spent 240 s on data grants and a debug attach, and the developer said "I mean in code").
  - **A step stops only what it started, by PID**: a test task once ran `Get-CimInstance Win32_Process ... Where
    CommandLine -match 'server.js' | ForEach-Object { Stop-Process -Id ... }` and stopped 9 node processes - its own 2
    and 7 others. The guard (every step, every mode) refuses a kill by name or filter (`| Stop-Process`, `Stop-Process
    -Name`, `kill -Name`, `taskkill /IM|/FI`, `pkill`, `killall`, `wmic ... delete|terminate`, `Invoke-CimMethod
    Terminate`, `.Kill()`) and any command that both queries processes (Get-CimInstance, Get-Process, pgrep, pidof,
    tasklist, Get-NetTCPConnection, netstat, fuser, `lsof -t`, `ps aux`) and kills; `kill <pid>`, `kill $(cat pidfile)`,
    `Stop-Process -Id <pid>`, `taskkill /PID <pid>` work (23 of 23 cases, the incident's command among them). Every
    step and the manager are told to stop only the processes they started, by the PID they recorded.
  - **One Dev break per app folder**: a named mutex keyed on the folder; a second copy signals the first (an event
    the first waits on opens its window) and exits - two copies wrote factory.json over each other and a finished
    task was lost. Tested: the second copy exits 0, the first stays.
  - **The manager's proposals for the factory are shown**: a box on the task's card, "The manager proposes these
    changes to the factory - for you to approve", numbered, with **Copy** and **Got it** (`FixesSeen`); before, they
    showed only when the manager handed the task to the developer.
  - **Harness levels** (`FactoryHarness`, chosen per task in the form, `Harness`; the level it runs with, `Lane`,
    `LaneWhy`), measured for one call on a developer machine with a large setup (dozens of plugins, ~200 skills, ~20 MCP
    servers): **Full** - everything the developer has, all hooks - ~19 s to start, 57k tokens of context (more in a
    repo with a big CLAUDE.md);

## Game (`Game.cs`)

Local only, in `game.json` next to the exe: `Events` (`record GameEvent(At, Kind "question"|"lesson", Tab, Topic,
Score?, Xp, Lesson?)`), earned `Badges` (`record EarnedBadge(Id, At)`) and `GoalDays` (dates the daily goal was met).
- **XP**: a checked answer `10 + score*10` (10-110); Show answer without checking 5; a lesson marked done 50 (undo
  removes that event and its XP; badges stay); daily goal bonus 100. Total XP = sum of events + 100 per goal day.
- **Ranks** (`record Rank(Name, From, Color)`): Junior 0 `#607D8B`, Mid 1000 `#2E7D32`, Senior 3000 `#1565C0`, Staff
  7000 `#6A1B9A`, Principal 15000 `#C62828`.
- **Daily goal**: 3 questions (checked or shown) and 1 lesson on the same day; awarded once per day.
- **Streak**: days in a row with any event, counted back from today (or from yesterday while today is empty); also
  the best streak ever.
- **Badges** (`record Badge(Id, Icon, Name, Description)`, emoji icons): First answer (first checked answer), Perfect
  10, Hat-trick (last three checked answers all 10), Century (100 questions), Polyglot (a checked answer in every
  topic except Mix), First lesson, Scholar (25 lessons), Graduate (every lesson of a course done), On fire (5-day
  streak), Unstoppable (14-day streak), Goal getter (goal met on 7 days), Night owl (question after 22:00), Early bird
  (question before 08:00).
- After every event: check the goal, then badges not earned yet, then a rank change; save; raise
  `event Action<IReadOnlyList<string>> Awarded` with the lines to celebrate ("+70 XP", "Daily goal complete! +100 XP",
  "<icon> Badge unlocked: <name>", "Rank up: <rank>!"). `LessonUndone` raises it with no lines.
- **Weak topics asked more**: `TopicWeight(topic)` = 1 for a topic with no checked answers, else `1 + (10 - average

- Calls: `QuestionAnswered(tab, topic, score)` after scoring; `QuestionSeen(tab, topic)` on Show answer;
  `LessonDone(course, index, title, courseFinished)` / `LessonUndone(course, index)` from Mark as done.

## How a conversation reads (`Turns.cs`)

The same in every chat (discussions and sessions): the developer's message in a tinted section (violet tint, a 3 px
violet left edge, a small "YOU" label); Claude's answer under a small coral "CLAUDE" label, plain; 18 px between
turns. A new answer is scrolled to **its start** (after layout, the label's position is brought to the top), not to
the bottom - it is read from the top. The discussion prompts ask Claude to start with the direct answer in one or two
sentences, then details: short paragraphs, a list only for several parallel points, bold only for the one key point,
at most one code block unless needed, no repeating the question, no closing summary.

## Code rendering (`CodeRenderer`)

`Render(text)` → `FlowDocument` (Segoe UI, left aligned, not justified); `Append(document, text)` for the chat.
- Prose takes the light Markdown Claude writes: `#`-`####` headings (bold, 17 / 15.5 pt); `- ` / `* ` / `• ` bullet and
  `1. ` / `1) ` numbered lines as real WPF `List`s (Disc / Decimal; a line without a marker right after an item
  continues it); inline `**bold**` (may hold inline code), `*italic*` / `_italic_`, `[text](https://...)` and bare
  `https://` URLs as links that open in the browser (trailing punctuation stays text).
- Fenced blocks ```` ```lang ```` → a dark box (`#1E1E1E`, Cascadia Mono / Consolas) coloured like VS Code Dark+:
  keywords `#569CD6`, strings `#CE9178`, comments `#6A9955`, numbers `#B5CEA8`, types (PascalCase) `#4EC9B0`, functions
  (word before `(`) `#DCDCAA`, plain `#D4D4D4`. Token regexes for C-like languages (java, js/ts, c#, kotlin...),
  SQL (case-insensitive keywords, `--` comments) and hash-comment languages (bash, python, yaml...).
- Inline `` `code` `` → code font in `#C7254E`. Everything else plain text.
- Tables: a `| a | b |` header row followed by a `|---|` rule (`:--`, `:-:`, `--:` set left / center / right) → a
  real table: bold header on a violet tint, thin cell borders, inline Markdown in cells, as many cells per row as the
  header has (extra dropped, missing empty); `\|` is a bar inside a cell.
- A path to an image or video on a local drive (`C:\...\x.png|jpg|jpeg|gif|webp|bmp|mp4|m4v|mov|webm|mkv|avi`, also
  inside `` `code` ``, where it may have spaces) that exists becomes a link that opens it in Windows' own app; an
  image also shows as a thumbnail (up to 360×220) that opens it. A network path or a mapped network drive stays plain
  text (looking at it would make Windows connect to that server), so does a missing file.
- Fenced code is a **code card** (a `BlockUIContainer`): a header with "<language> · N lines", **Copy** (copies the
  code; "Copied ✓") and, for code over 12 lines, **Show all N lines** / **Hide**; such code starts folded to its
  first 6 lines with a fade at the bottom. The buttons are plain text on the dark card (their label is their
  accessible name).
- ```` ```mermaid ```` blocks are drawn as diagrams (`DiagramRenderer`, native WPF, no packages), in the notebook
  colours, inside a card, scaled down to fit (never up); a block it cannot read stays a code block.
  - `flowchart LR|TD` (also `graph`): nodes `id`, `id[box]`, `id(round)` / `id([stadium])`, `id{decision}` (lime
    diamond), `id[(database)]` (violet cylinder), `id((circle))`; links `-->`, `---`, `-.->` (dashed), `==>` (thick),
    with `|label|` or `-- label -->`; chains `A --> B --> C`; `;`-separated statements; `subgraph`/`style`/`class` lines
    ignored; `<br>` breaks a label. Layout: ranks by the longest path (edges that close a cycle ignored), nodes in a rank
    ordered by their parents, centred; arrows from box edge to box edge, labels on a paper-coloured tag. At most 40 nodes.
  - `sequenceDiagram`: `participant` / `actor` (`as` label), messages `->>`, `-->>` (dashed reply), `->`, `-->`, `-x`,
    self-messages as a loop, `Note over A,B:` / `left of` / `right of` (lime); participant boxes at top and bottom,
    dashed lifelines; columns widen to fit their labels. `autonumber`, `activate`, `loop`/`alt`/`end` lines are left
    out of the picture. At most 10 participants.
- Discussions and lessons are told (`QuestionGenerator.Diagrams`): "When a picture explains it better than words - a
  flow, an architecture, a sequence of calls between services - draw one small diagram as a ```mermaid block, as in a
  good tutorial" (flowchart LR/TD with the node and arrow forms above, or sequenceDiagram), at most 10 nodes, short
  labels, no styling, and none when it adds nothing.
